# Pyxis / GeckoOS — Full Codebase Audit (2026-08-05)

Read-only audit pass across both repos (`geckos/`, `pyxis-experience/`) against
the claims in `CLAUDE.md`, `PROJECT_STATUS.md`, and
`pyxis-experience/INTEGRATION_NOTES.md`. Nothing was changed. Companion to
[`ALPHA_ROADMAP.md`](ALPHA_ROADMAP.md), which turns these findings into a
release plan.

Every finding below cites the file (and line where it's a specific claim) it
came from, so it can be re-verified rather than trusted.

---

## 0. Executive summary

**The architecture is done and it is genuinely good.** The compositor-first,
IPC-driven model you set out to build — descended from LunaSysMgr's layer
compositing and Firefox OS's `mozApps`/bridge model — exists as working code:
Evo composites real Wayland clients, Echo routes real messages, Nova is a real
app-identity/launch layer, vela is a real from-source Gecko with a real
`pyxis://` scheme and a real compiled-in `window.geckoOS` bridge, and Bloom
talks to all of it over that bridge. That is the hard part, and it is behind
you.

**What's missing is not architecture — it's the last mile in three places:**

1. **The rootfs is missing binaries that services shell out to.** `opkg`,
   `nmcli`, and a working `shutdown`/`systemctl` are all absent from the
   image, so the Installer service, the network indicator, and every power
   action fail at runtime no matter how correct the Rust is. This is the
   single highest-leverage fix in the whole audit: three lines in
   `scripts/create-rootfs.sh` unblock a whole tier of "broken" features.

2. **The shell's app list is a hardcoded TypeScript array.** `PYXIS_APPS` in
   `pyxis-experience/src/apps/registry.ts` is the *only* source of apps for
   the launcher, drawer, and search. Nothing in the shell ever calls
   `nova.List`. So: the Installer app you built and package isn't even in the
   list (unreachable from the UI), and **no app installed via `.ipk` can ever
   appear on the desktop.** For "I need all my apps working," this is the
   blocker.

3. **A handful of small, high-visibility correctness bugs** — a frozen clock,
   a directory listing that aborts wholesale on one unsupported `statx` field,
   no shutdown/logout/lock anywhere in the UI, no notification surface.

**Doc drift is significant.** Several prominent items in `CLAUDE.md` are stale
(fixed or renamed since) — see §7. Fixing those is cheap and stops future
sessions chasing already-solved problems.

## 1. Runtime blockers — services calling binaries that aren't in the image

This is the highest-value section. All three are real, all three are
`scripts/create-rootfs.sh` one-liners.

### 1.1 `opkg` is never installed — the Installer can never work

`echo/src/services/installer.rs` is real, careful code (760 lines: path
confinement, metadata-without-install, progress signals, Nova registry refresh
after each op). Every mutating path gates on `Self::require_opkg()`
(`installer.rs:535-538`), which errors with `"opkg is not available on this
system"` when `which_opkg()` returns `None`.

`opkg` appears **nowhere** in `scripts/create-rootfs.sh` — not in the
`apt install` list (`create-rootfs.sh:292-311`), not in `stage_binaries()`
(`:1017-1045`), nowhere. The only occurrence of the string in `scripts/` is a
comment at `:1367`.

**Consequence:** `installer.Install` and `installer.Remove` fail 100% of the
time on-device. `ListInstalled` returns an empty map (`installer.rs:515-517`
short-circuits when opkg is absent), so the Installer app renders as if
nothing is installed. This is why item "Installer present / install flow" has
never passed a test — it was never runnable.

**Fix:** add `opkg` to the apt list. Debian ships it (`opkg` package). Verify
its config (`/etc/opkg/opkg.conf`) points `dest root /` and that
`--force-depends`/architecture (`arch all`, plus your target arch) match what
Vroom stamps into `CONTROL/control` (`vroom/src/control.rs`).

### 1.2 `nmcli` is never installed — the network indicator is permanently "offline"

`echo/src/services/network.rs:12-30` implements `get_status()` by running
`nmcli -t -f ACTIVE con show --active` and setting
`connected = output.is_ok() && !output.unwrap().stdout.is_empty()`.

NetworkManager is not in the base package list. Boot brings the NIC up with
**BusyBox `udhcpc`** instead (`create-rootfs.sh:703`), which nmcli knows
nothing about. So `Command::new("nmcli")` returns `Err`, `connected` is
`false`, and:

- `TopSystemBar.tsx` renders `WifiOff` forever.
- `QuickSettingsMenu.tsx` shows "Not connected" forever.
- Settings → Network shows a disconnected state forever.

…on a machine that has a working DHCP lease.

**Fix (recommended):** don't add NetworkManager to a BusyBox-init image. Rewrite
`NetworkService::get_status()` to read the kernel directly — `/sys/class/net/*/
operstate`, `/sys/class/net/*/device` (to skip `lo`/`dummy0`/`sit0`, the same
filter `create-rootfs.sh:690-700` already worked out the hard way), and
`ip route get 1.1.1.1` or `/proc/net/route` for default-route presence.
`get_interfaces()`/`get_ip_address()` already shell out to `ip` (present via
`iproute2`) and are fine as-is; only `get_status()`/`get_type()` are
nmcli-dependent.

### 1.3 Power actions can't work — no systemd, no `shutdown`

`echo/src/services/power.rs` implements `shutdown`/`reboot` via
`Command::new("shutdown")` (`:15-44`) and `sleep()` via
`systemctl suspend` (`:46-57`).

BusyBox is PID 1 (`create-rootfs.sh:485-522`, `::wait:/usr/sbin/geckoOS-boot`)
and there is no systemd running (the boot script says so explicitly at
`:741`: "no dbus-daemon started anywhere in this script"). `util-linux`'s
`shutdown` talks to init over a protocol BusyBox init doesn't speak the same
way, and `systemctl` isn't running an instance to talk to.

**Fix:** for a BusyBox-init image the correct calls are
`busybox poweroff`/`busybox reboot` (or `kill -USR2 1` / `kill -TERM 1` per
BusyBox init's signal table). `sleep()` has no backend at all in this image —
either implement it against `/sys/power/state` (`echo mem > /sys/power/state`)
or have it return a structured "unsupported on this platform" error rather
than a spurious success.

Note also: **nothing in the UI calls any of these.** Grep across
`pyxis-experience/src` and every app package returns no `shutdown`, `reboot`,
`logout`, or `lock` call site. See §4.1.

### 1.4 No audio stack at all

`create-rootfs.sh:268-270` conditionally picks up `libasound2` — a *client
library*. There is no ALSA config, no PipeWire, no PulseAudio, no
`alsa-utils`. Vela/Gecko will initialise its audio backend and find nothing.

Not a bug so much as an unscoped subsystem: **there is currently no audio on
Pyxis, and no plan document covers it.** For a "full desktop environment" this
needs to be an explicit roadmap item (see `ALPHA_ROADMAP.md` §Alpha 5), not an
assumption.

### 1.5 `acpi` absent (benign)

`power.rs:68-77` tries `acpi -b` first and falls back to
`read_battery_from_sysfs()`. `acpi` isn't installed, so the sysfs path always
runs — which is the correct path anyway. Under QEMU there's usually no
`/sys/class/power_supply/BAT*` either, so battery renders as `—`. Working as
designed; worth making the UI's "no battery present" state deliberate rather
than incidental.

## 2. The app-registry gap — why "all my apps" can't work yet

### 2.1 The shell's app list is static and hardcoded

`pyxis-experience/src/apps/registry.ts` exports `PYXIS_APPS`, a literal array
of 7 entries. Every consumer reads from it:

| Consumer | File | Use |
|---|---|---|
| Pinned launcher strip | `src/components/LeftLauncher.tsx:12-17` | `PYXIS_APPS.filter(a => a.pinned)` |
| App drawer | `src/components/AppDrawer.tsx:16-18` | `PYXIS_APPS.filter(...)` |
| Desktop search | `src/components/DesktopSearch.tsx` | via `mockApps` |
| Dock icons | `src/components/BottomDock.tsx:13` | `APP_ICONS` built from `PYXIS_APPS` |
| Window sizing | `src/hooks/useWindows.ts:3` | `appById()` |

`useAppHost()` *does* expose a live `manifests` array
(`packages/app-sdk/src/useEcho.ts:412, 604`, fed by `appHost.ListApps`), but
it is used in exactly one place — `LeftLauncher.tsx:139`, only to look up a
display name for an app that's already in the static list.

**Nothing in the shell ever calls `nova.List`.** The SDK doesn't even expose a
wrapper for it (`useEcho.ts` has `launchApp`/`focusApp`/`openExternalBrowser`
against `org.geckoOS.nova`, but no `List`/`GetInfo`; the *mock* path in
`EchoClient.ts:689-698` handles `List`/`GetInfo`, so the plumbing is half
there).

**Consequences:**

1. **Any `.ipk` app a user installs is invisible.** Nova discovers it
   (`nova.rs:628-630` scans `/usr/pyxis/applications` as `AppTier::Opkg`),
   AppHost can launch it, `pyxis-appctl` can list it — but the desktop will
   never show it. The entire Vroom SDK/PDK → Installer → Nova pipeline
   terminates at a UI that can't see its output.
2. **The Installer app itself is unreachable.** It's built
   (`packages/apps/installer/`), packaged (`.pyxis/` artifacts present), and
   staged into the rootfs (`create-rootfs.sh:1365-1377` `stage_installer_app`)
   — but `installer` is **not** in `PYXIS_APPS`. Grepping `src/` for
   "installer" returns nothing. There is no way to open it from the desktop.
3. Icons for third-party apps have no path — `PyxisAppDef.icon` is a
   `LucideIcon` *component reference*, not a URL. A dynamic registry needs an
   icon-URL field (`pyxis://<id>/icon.png` or a `nova.GetInfo` icon path) with
   the Lucide set as a fallback for built-ins.

**This is the #1 functional gap in the project.** Everything else in the app
pipeline is built.

### 2.2 `entryHtml` still points at dev-server ports

`registry.ts` entries carry `entryHtml: 'http://localhost:5180/index.html'`
etc. In compositor mode this is unused (launch goes through `nova.Launch`, and
`Desktop.tsx:246` gates `DesktopWindow` behind `!IN_COMPOSITOR`), so it isn't
*breaking* anything today — but it's a landmine: the moment anyone renders a
window outside dev, it points at nothing. It should be `pyxis://<id>/index.html`
with the localhost port kept only as a dev override.

### 2.3 Path convention: docs say `/usr/palm`, code says `/usr/pyxis`

`CLAUDE.md`'s Nova entry says it "scans `/usr/palm/applications/*/appinfo.json`".
The code scans `/usr/pyxis/applications` (`nova.rs:61, 629`), which matches
Vroom (`vroom/src/config.rs:340-342`) and the spec's own explicit note that
the webOS path was deliberately dropped
(`vroom/docs/pyxis-sdk-pdk-spec.md:60-61`). **Code and spec agree; only
CLAUDE.md is wrong.** Easy fix, but worth doing — this is exactly the kind of
stale line that sends a future session hunting a nonexistent bug.

## 3. Correctness bugs found by reading (not yet observed on-device)

### 3.1 `readDirectory` aborts the whole listing if any entry lacks a birth time — likely root cause of Files #3

`echo/src/services/filesystem.rs:27-48` builds each entry with (timestamps at
`:40-45`):

```rust
"modified": metadata.modified()?.duration_since(UNIX_EPOCH)?.as_secs(),
"created":  metadata.created()?.duration_since(UNIX_EPOCH)?.as_secs(),
```

Both `?`s are inside the `for entry in fs::read_dir(...)` loop, so **a single
failing entry aborts the entire directory read** and returns `Err`. `FilesApp`
then hits its `if (res?.error || !res?.entries)` branch
(`packages/apps/files/src/FilesApp.tsx:170`) and renders nothing — precisely
the reported symptom, "file entries are not displaying properly."

`std::fs::Metadata::created()` returns `Err(ErrorKind::Unsupported)` on Linux
whenever the kernel/filesystem doesn't report `STATX_BTIME`. That includes
**tmpfs, overlayfs, procfs, sysfs**, and older ext4 inodes created with a
256-byte inode size. The Files app starts at `HOME` (`FilesApp.tsx:102`), so
whether it trips depends on what's in `/home/geckouser` — but any traversal
into `/tmp`, `/run`, `/proc`, or `/sys` is a guaranteed failure, and a
`.gitkeep`-era ext4 inode is enough to break `$HOME` too.

**Fix:** make both timestamps non-fatal —
`metadata.created().ok().and_then(|t| t.duration_since(UNIX_EPOCH).ok()).map(|d| d.as_secs())`
→ serialize as `null` when unavailable. Same for `modified`. Also wrap the
per-entry `entry.metadata()?` so an unreadable symlink target doesn't kill the
listing. This is a ~6-line change and I'd bet on it being the whole of #3.

### 3.2 `readFile` is UTF-8-only and will error on any binary file

`filesystem.rs:70` uses `fs::read_to_string`, which returns `Err` on invalid
UTF-8 regardless of the `encoding` parameter the caller passed (the parameter
is accepted and echoed back but never acted on). This blocks image preview in
Files and any binary read. Known/tracked, restated here with the line.

**Fix:** branch on `encoding` — `utf-8` keeps current behaviour;
`base64` → `fs::read` + base64-encode. Add a `maxBytes` guard so a 4 GB file
can't be pulled through the IPC bus.

### 3.3 The clock is frozen

`pyxis-experience/src/components/TopSystemBar.tsx:48-51`:

```tsx
const currentTime = new Date().toLocaleTimeString('en-US', { ... });
```

Computed once per render with no timer. `TopSystemBar` only re-renders when
its props or the battery/network hooks change, so the clock displays boot time
and then sits there. On a desktop that's an immediately visible "this is
broken" signal.

**Fix:** `useEffect` + `setInterval(…, 1000)` (or align to the next minute
boundary), storing into state.

### 3.4 Every top-bar icon opens the same menu

`TopSystemBar.tsx:106-137`: the Bell, Settings, Wifi, and Battery buttons all
call `onToggleQuickSettings`. There is no notification centre, no separate
network panel, no separate battery panel. `QuickSettingsMenu.tsx:59-63`
hardcodes the string "No new notifications" — it is not wired to
`org.geckoOS.notification` at all.

### 3.5 Quick-settings toggles are decorative

`QuickSettingsMenu.tsx`: "Notifications", "Auto-brightness", "WiFi Enabled",
"Low Power Mode", "Battery Percentage" all have `onChange={() => {}}` or no
handler. Only "Dark Mode" is real (`setSetting(SETTING_KEYS.theme, …)`). For a
pre-beta these should either be wired or removed — a desktop full of dead
switches reads worse than a smaller honest panel.

### 3.6 Notification service can't deliver anything

`echo/src/services/notification.rs:35-45` shells out to `notify-send`, which
requires a running org.freedesktop.Notifications D-Bus service. There is no
D-Bus session bus in this image and no notification daemon. `close_all()`
(`:66-77`) shells out to `dbus-send` for the same reason.

The service *always returns success* regardless (`:47-55` builds an `Ok`
response ignoring `_result`), so callers can't even tell it failed.

**Fix:** this shouldn't shell out at all. Notifications should be an Echo-native
concept: `notification.Show` stores the notification and **broadcasts an Echo
signal** that Bloom subscribes to and renders in its own notification centre.
That's both the webOS model (LS2 + the notification manager in the shell) and
the Firefox OS model, and it removes the freedesktop dependency entirely.

### 3.7 Shift's entire Echo surface is mocked

`shift/src/echo_ipc.rs:369-505` — every handler is a stub with a `TODO`:

- `handle_launch_process` returns a hardcoded `pid = 1000u32` (`:378-381`)
- `handle_list_processes` returns a literal
  `[{pid: 1000, app_id: "firefox"}, {pid: 1001, app_id: "thunderbird"}]`
  (`:461-465`) — fabricated data with app ids that don't exist in Pyxis
- `handle_get_process` / `handle_get_resource_usage` return hardcoded
  `memory_mb: 128, cpu_percent: 5.0` (`:447-452`, `:487-494`)
- `handle_kill_process`, `handle_suspend_process`, `handle_resume_process`,
  `handle_set_resource_limits` do nothing but log and emit a success signal

Meanwhile `shift/src/process.rs`, `resources.rs`, `lifecycle.rs`, `tree.rs`
(~2,250 lines total) contain the *real* implementations, and `shift-daemon`
does run at boot (`create-rootfs.sh:709`) and does `register_echo()`.

So Shift is a daemon that starts, registers on the bus, and then answers every
question with fiction. Nothing currently consumes it (AppHost owns app
processes), so it's not actively harming anything — but any future consumer
will get plausible-looking garbage, and it undercuts the `process` service
story. **Either wire the handlers to the real `Shift` methods, or don't
register the interface at all until they are.** Silence beats fake data.

### 3.8 SIGSTOP suspend doesn't reach Gecko's content processes

`apphost.rs:502-504` sends `SIGSTOP` to `session.pid`. For a Nova-launched app
that's the `setpriv`→`vela` parent. Gecko is multi-process: content processes
are children with their own pids and keep running, scheduling, and burning
battery while the app is "suspended."

This is exactly what Puppis's `suspend_app`/`resume_app` freeze-thaw was
extracted to handle (`puppis/src/gecko_app_launcher.rs`), and it's still not
wired (roadmap item 3). Worth noting that the current suspend is a *partial*
suspend, not a no-op — the UI-thread freeze is real, the resource win isn't.

## 4. Missing features for a "full desktop environment"

Things a user would expect that have no implementation anywhere in either
repo. Grepped for, not found.

### 4.1 Session control: no shutdown, reboot, logout, lock, or suspend UI

No call site anywhere in `pyxis-experience` for any power action. There is no
lock screen, no logout, no session-end path at all. The only way to end a
Pyxis session is to kill the VM.

For webOS/Firefox OS parity this is a first-class shell responsibility. Needs:
a power menu (quick-settings or launcher), a lock screen surface (a
`wlr-layer-shell` `overlay` client, or a dedicated Evo lock mode that
suppresses all other input), and working `power.rs` backends per §1.3.

### 4.2 Notification centre

Covered in §3.4/§3.6 — no UI, no working service, no signal path. A desktop
without notifications isn't pre-beta.

### 4.3 Window resizing

Already tracked as alpha2 punch-list #11. Confirmed by reading:
`PointerResizeSurfaceGrab`/`TouchResizeSurfaceGrab` exist in
`evo/src/shell/grabs.rs` and are wired to client-initiated `resize_request`,
but nothing on the SSD side draws or hit-tests resize edges. **However** —
see §5.1: the current decoration model means most app windows are GTK-decorated
and get GTK's own resize handles, so the real scope here is narrower than the
punch-list implies. Worth re-scoping before building.

### 4.4 Display settings

`evo/src/udev.rs:1460` notes HiDPI scale is hardcoded rather than read from the
render surface. There's no multi-monitor UI, no resolution picker, no scale
setting. Settings has four sections (`SettingsApp.tsx:30-35`: Appearance,
Network, System, About) and none of them is Display.

### 4.5 wlr-layer-shell surfaces are accepted but never composited

Tracked in `PROJECT_STATUS.md`. Restating because it gates three roadmap items
at once: a real wallpaper layer, a lock screen, and any future panel/OSD all
want layer-shell. Right now Bloom fakes all of it by being one fullscreen
kiosk window pinned to `RenderZindex::Background`, which is why "show desktop",
shell transparency, and shell-restart-survives-wallpaper are all impossible.

### 4.6 No permission UI

Nova has a real permission vocabulary and deny-by-default capability mapping
(`nova.rs:194-232`) — but nothing surfaces it. There is no install-time prompt,
no per-app permission screen in Settings, no runtime grant flow. Firefox OS's
whole trust story was the manifest `permissions[]` + a visible grant model;
the back half of that is unbuilt.

### 4.7 No input/locale/accessibility settings, no clipboard manager, no screenshot

Minor individually, collectively the difference between "a shell" and "a
desktop." `evo/src/enhancements/data_device.rs` exists (clipboard/DnD
plumbing) but nothing in Bloom uses it. `screencopy.rs` exists (and
`:385` notes the buffer path is "simplified: just clear the buffer for now")
— it's the intended source for dock thumbnails and screenshots, neither built.

## 5. Design tensions worth resolving before more building

### 5.1 The decoration model contradicts itself between code and status board

`create-rootfs.sh:960-990` documents a decision revised on 2026-07-08 after
live QEMU debugging:

> "the model is now: ordinary app windows keep GTK's own working titlebar and
> Evo draws no SSD; the desktop SHELL (Bloom) must instead be fully
> chromeless."

But `PROJECT_STATUS.md`'s Evo section still tracks #8 (thin window border) and
#9 (title bar shows app name) as SSD features with "visual polish still
required," and #11 (resize) is scoped as "SSD header bar draws no resize
handles."

**These can't both be true.** If GTK owns app-window decoration, then #8/#9/#11
are either moot (GTK already provides all three) or they're about a *different*
set of windows (native non-GTK clients, XWayland clients). If Evo is supposed
to own SSD, then the boot script's GTK-titlebar concession is a workaround to
be removed, not the model.

**This needs an explicit decision before alpha3 work starts**, because #7
(maximize→unmaximize crash) sits right on the seam — a crash during a
maximize/unmaximize configure cycle is exactly what you'd expect from two
parties disagreeing about who owns the frame geometry. I'd resolve #5.1 *first*
and re-diagnose #7 afterward; there's a decent chance they're the same bug.

**My read:** GTK-decorates-apps is the pragmatic right answer for now (it's
what actually works, and matching GTK's decorations is a rabbit hole), and Evo
SSD should be scoped down to non-GTK/XWayland clients only. But it's your
call, and the docs should say one thing.

### 5.2 Rockhopper's role overlaps Nova/AppHost and isn't defined

`rockhopper/` is ~2,900 lines and its daemon runs at boot
(`create-rootfs.sh:1003`). It owns `wayland.rs`, `dbus_session.rs`,
`elf_loader.rs`, `compatibility.rs`, and uses Puppis's `GeckoAppLauncher`. But
app launching now lives in Nova→AppHost, and `compatibility.rs:188` returns
`ENOSYS` for the interesting cases. `PROJECT_STATUS.md` itself flags "role vs
Nova/appHost worth clarifying."

It's shipping in the image and consuming boot time. Either give it a defined
job (the Firefox OS-era compat layer it was designed as, which nothing
currently exercises) or stop starting it.

### 5.3 Terminal: web-view vs native

Under evaluation per `PROJECT_STATUS.md` #2. Data point from the audit: the app
uses `xterm@5.3.0` + `xterm-addon-fit@0.8.0`
(`packages/apps/terminal/package.json`), which are the **deprecated** package
names — the maintained line is `@xterm/xterm` / `@xterm/addon-fit`. If you stay
web-view, migrating is a prerequisite for getting the QOL fixes (the
deprecated packages don't get them). If you go native, that decision moots it.

I'd stay web-view: a native terminal breaks the "every app is a pyxis:// web
app" story that makes the SDK coherent, and the actual QOL complaints
(tab completion, history) are shell-side and already work — the gap is
terminfo/keymap fidelity, which `@xterm/xterm` + a correct `TERM` handles.

### 5.4 Zero test coverage on the UI side

`find pyxis-experience -name "*.test.*"` → 0 results. No Vitest, no Testing
Library, no Playwright. The Rust side is much better: **177** `#[test]`/
`#[tokio::test]` functions across 41 files, including real coverage in
`nova.rs`, `apphost.rs`, `installer.rs`, `routing.rs`, `transport.rs`.

The asymmetry matters because the bugs that keep escaping to on-device testing
(#3 Files, #10 dock restore) are all in the JS↔bridge seam, which is exactly
what has no tests. A contract-test suite against `EchoClient`'s mock — asserting
the mock's response shapes match the Rust services' actual JSON — would have
caught the Files response-shape class of bug at the desk.

## 6. Diagnostic notes on the open alpha2 punch-list items

Read-only tracing; these narrow the search rather than close it.

### #3 Files app — very likely §3.1

`readDirectory`'s `created()?` abort. Highest-probability single cause, and
cheap to eliminate. Do this before any on-device tracing.

Response shape itself checks out: `filesystem.rs:33-46` emits
`{name, path, isFile, isDirectory, isSymlink, size, modified, created,
permissions}` inside `{entries, path, count}`, and `FilesApp.tsx:44-64`
consumes `entries[].{name, path, isDirectory}`. No mismatch — which supports
the "whole call errored" theory over the "shape is wrong" theory.

### #10 restore-from-dock — the IPC path is sound; suspect identity

I traced the full chain and **every link exists and looks correct**:

`BottomDock` orphan click → `Desktop.tsx:100-110 handleOrphanSelect` →
`echo.focusApp` (`useEcho.ts:131-140`) → `nova.Focus`
(`daemon.rs:2027-2031`) → `Nova::focus` (`nova.rs:1012-1039`) →
`bus.call_method("org.geckoOS.evo", …, "FocusWindow")` → Evo
`echo_ipc.rs:992-1007` queues a `WindowAction::Focus` **and replies**
(so there's no hang) → drained by `process_pending_window_actions`
(`state.rs:1850`), called every loop iteration in all three backends
(`udev.rs:542`, `winit.rs:451`, `x11.rs:485`) → `raise_window`
(`state.rs:1765`) which explicitly un-minimizes first (`:1776-1784`, with a
comment describing this exact bug) → `unminimize_window` re-maps into `space`
and emits `WindowMinimized{minimized:false}` → `daemon.rs:1961-1976` routes it
to `Nova::handle_window_restored` → `AppHost::resume` → `SIGCONT`.

That chain is complete. So the failure is almost certainly **before** it, at
identity resolution. Two concrete candidates, in order:

1. **`Nova::focus` errors at `nova.rs:1016-1019`** —
   `session.surfaces.first()` is `None` → `"app '<id>' has no mapped
   compositor window yet"`. This happens if the app's *Wayland* `app_id`
   (read at `state.rs:1675-1686` from `XdgToplevelSurfaceData`) differs from
   Nova's app id. When it differs, `bind_surface` (`apphost.rs:724-746`) finds
   no matching session and **synthesizes a second one** under the Wayland
   app_id, carrying the surfaces — leaving Nova's original session with a pid
   but zero surfaces. The dock would then show a *second*, generic-globe icon
   (unknown to `PYXIS_APPS`), and focusing the real one would fail.

   **Check first:** on-device, `pyxis-appctl list` (or `appHost.ListRunning`)
   right after launching an app. **Two sessions for one app = confirmed.**
   The vela patch that stamps `PYXIS_APP_ID` into `WM_CLASS`/xdg app_id
   (`gecko/patches/pyxis/browser/base/content/browser-init.js.PYXIS_DIFF`,
   `BrowserContentHandler.sys.mjs.PYXIS_DIFF:132-140`) is what's supposed to
   prevent this — verify it actually took in the built binary.

2. **`Nova::focus` errors at `nova.rs:1013-1015`** — `find_session_by_app`
   returns `None` because the session already `finalize_exit`'d. Less likely
   given the icon is visible.

Both produce a user-visible error snackbar via `Desktop.tsx:104-108`
("Couldn't reach <appId>"). **If no snackbar appears on a failed dock click,
neither theory holds** and the problem is that the click isn't reaching
`handleOrphanSelect` at all — which would point at the dock's orphan-vs-window
branch, not the IPC. That's a one-glance discriminator worth using first.

## 8. What's genuinely solid (so it doesn't get re-litigated)

Worth stating explicitly, because an audit that only lists problems misleads.

- **Evo** (~16.5k lines) is a real Smithay compositor: XDG + XWayland,
  layer-shell acceptance, workspaces, DRM/udev + winit + x11 backends,
  screencopy, real input. The Echo integration (`enhancements/echo_ipc.rs`,
  1,600 lines) is thoughtful — a tokio broker thread with a drained action
  queue so IPC never touches `Space`/`Seat` off-thread.
- **Echo** is a real bus with real routing, registration, forwarding, and
  signal broadcast, hosting 12 services, with genuine unit tests.
- **Nova** (~1,900 lines) does everything it claims: multi-root discovery with
  a real tier/trust model (`AppTier`, `tier_may_claim_id`), origin mapping,
  install with sha256 + atomic swap, single-instance policy, per-app profile
  provisioning with correct ownership for the setpriv drop, permission
  vocabulary mapping.
- **The vela patch set is real and substantial** — a full `pyxis://` protocol
  handler with parent/child IPDL channels
  (`gecko/patches/pyxis/netwerk/protocol/pyxis/`, 14 files including
  `PPyxisChannel.ipdl`), a `JSWindowActor` bridge pair
  (`toolkit/actors/PyxisBridge{Parent,Child}.sys.mjs`), `PBackground` wiring,
  and `--pyxis-app` kiosk plumbing. This is the part everyone said couldn't be
  done anymore, and it's done.
- **`scripts/create-rootfs.sh`** is one of the better-commented build scripts
  I've read — the inline provenance notes (the `dummy0` NIC discovery at
  `:690-700`, the `rsync -aL` symlink diagnosis at `:1080-1095`, the seatd
  requirement at `:733-745`) are real debugging knowledge captured at the point
  of use. Keep doing that.
- **Vroom** is a complete packaging toolchain — config validation, staging,
  ipk emission with a built-in writer fallback, web + native builders, device
  profiles, templates, `doctor`/`lint`/`inspect`.
